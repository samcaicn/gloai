> 目标项目：tupai（d:\1data\ai\tupautochromium）

## 一、方向调整说明

v0.1 计划（已废弃删除）的策略是"借鉴 BitFun UI 框架 + 保留 tupai 域内代码"。**本次方向调整为"全面用 BitFun UI 增减"**：
- 现有 23+ .jsx（App.jsx, Sidebar.jsx, HomePage.jsx, AutomationPage.jsx, TasksPage.jsx, SessionHistory.jsx, SettingsModal.jsx, SkillChatPage.jsx, WecomPage.jsx, ImChatPage.jsx, SkillEditorPage.jsx, FloatingWindow.jsx, flowchart/*）**全部重写**
- tupai 域内业务（trace-auto 录制 / IM 渠道 / 桌面自动化 / 自进化 / 设备注册）**保留在 Rust 后端**，通过 Tauri command 桥接到 BitFun UI
- 多品牌（tupai + safeopc）双 NSIS 流程 **保留**
- 网络特殊性（api.tuptup.top 走 mcp_proxy + `.no_proxy()`）**保留**
- 视觉品牌（赛博朋克霓虹默认）**保留**为默认主题，BitFun 原生 2 套色板作为备选

## 五、BitFun 克隆策略

### 5.1 版本锁定

| 策略 | 决策 | 理由 |
|---|---|---|
| 克隆方式 | `git subtree` 而非 `git submodule` | subtree 简单且可独立提交；submodule 麻烦 |
| 版本锁定 | 锁 `main` 分支 + 每周 rebase 窗口 | 避免 BitFun 频繁破坏性重构 |
| Tag 锁定 | 锁 `v0.2.x` 大版本（截至 2026-07-08 = v0.2.10） | 大版本内尽量兼容；跨大版本独立评估 |
| 冲突策略 | 优先保住 BitFun 兼容性，tupai 业务在包装层做适配 | 减少合并冲突 |
| 验证流程 | 每周一上午 `git subtree pull` 后跑 `pnpm tauri dev` | 早发现冲突 |

### 5.2 克隆实施命令

```bash
# 在 d:\1data\ai\tupautochromium\ 下
git subtree add --prefix=src/web-ui --squash https://github.com/GCWing/BitFun.git v0.2.10

# 后续同步
git subtree pull --prefix=src/web-ui --squash https://github.com/GCWing/BitFun.git v0.2.10
```

## 六、tupai 域内桥接层

### 6.1 桥接层设计

**目标**：BitFun UI 调用 → 桥接层 → tupai Rust 后端（Tauri command）

```
[BitFun UI 组件]
    ↓ import
[infrastructure/api/tupai/index.ts]  ← 桥接层
    ↓ invoke()
[Tauri 2 IPC]
    ↓
[src-tauri/.../commands/]            ← 域内实现
    ↓ 调用
[services/* / execution/*]            ← 6 层架构
```

### 6.2 桥接层文件清单（已实现，18 个 .ts 文件）

```
src/web-ui/src/web-ui/src/infrastructure/api/tupai/
├── index.ts                # 统一导出
├── types.ts                # 与 Rust 对齐的 TS 类型
├── events.ts               # 事件订阅（基于 @tauri-apps/api/event）
├── llm.ts                  # LLM 流式调用 → invoke('mcp_call_v2', action='llm.stream_request')（经 MCP）
├── mcp.ts                  # MCP 调用 → invoke('mcp_call_v2') / invoke('mcp_stream')
├── skill.ts                # Skill 执行 → invoke('skill_execute_*')
├── im.ts                   # IM 操作 → invoke('im_*')
├── recording.ts            # 录制 → invoke('recording_*')
├── automation.ts           # 自动化 → invoke('automation_*')
├── device.ts               # 设备 → invoke('register_device') / invoke('renew_device_token')
├── document.ts             # 文档 → invoke('doc_*')
├── memory.ts               # 长记忆 → invoke('memory_*')
├── computerUse.ts          # Computer Use → invoke('cu_*')
├── upgrade.ts              # 升级 → invoke('upgrade_*')
├── floater.ts              # 浮窗 → invoke('fw_*')
├── settings.ts             # 设置读写
├── tenant.ts               # 租户信息
└── theme.ts                # 主题色（与 Rust 解耦，前端独立）
```

### 6.3 关键约束（已落实）

- `llm.ts` 的 `LlmRequest` **不含 `model` 字段**（避免触发 'default' 字面量 SSE 错误）
- `im.ts` 的 `imSend` **含 `target` 参数**（LongConnAdapter relay gateway 路由必需）
- `events.ts` 提供 `subscribe<T>(event, handler)` 返回 unlisten 函数（基于 `@tauri-apps/api/event` 的 `listen`）
- `theme.ts` 与 Rust 解耦，纯前端 localStorage 持久化 `tupai-scheme`

### 8.3 Rust 轨道（8.5 周，与 UI 轨道并行）

#### 8.3.1 Rust 6 层架构定义

将现有 `src-tauri/src/` 单层结构重构为 6 层 24 crate，详见 `docs/rust-layer-architecture.md`：

| 层 | crate 前缀 | 职责 | 示例 |
|---|---|---|---|
| L1 interfaces | `tupai-if-*` | 接口定义/契约（trait + DTO） | `tupai-if-agent`, `tupai-if-skill` |
| L2 contracts | `tupai-co-*` | 跨层契约（事件/命令 schema） | `tupai-co-events`, `tupai-co-commands` |
| L3 adapters | `tupai-ad-*` | 外部系统适配器（IM/CDP/UIA/OCR） | `tupai-ad-im`, `tupai-ad-cdp` |
| L4 services | `tupai-sv-*` | 业务服务（领域逻辑） | `tupai-sv-skill`, `tupai-sv-recording` |
| L5 execution | `tupai-ex-*` | 执行引擎（自动化/自进化/调度） | `tupai-ex-automation`, `tupai-ex-evolution` |
| L6 assembly | `tupai-app-*` | 组装层（Tauri command + 入口） | `tupai-app-desktop`, `tupai-app-relay` |

**重构原则**：
- B-1~B-3：L1/L2 接口与契约先行（2 周）
- B-4~B-5：L3 适配器 + L4 服务迁移（3 周）
- B-6：L5 执行引擎整合（2 周）
- B-7：L6 组装 + 旧命令路径删除（1.5 周，最后做）

**双 lib 共存**：B 阶段全程保留旧命令路径，桥接层用旧命令名，B-7 阶段才删旧路径。

## 十三、DuckDB 本地数据中台设计

> 基于 Hermes-RS 架构，DuckDB 作为唯一本地结构化存储，替代现有 SQLite（rusqlite），过渡期两者共存。
> 7 张核心表 + FTS 全文索引 + HNSW 向量索引 + 场景隔离 + Rust 集成 + SQLite 迁移。
> 详见 `docs/hermes-rs-implementation.md`。

### 13.1 设计总则

| 维度 | 选型 | 说明 |
|---|---|---|
| 存储引擎 | DuckDB 1.1（embedded OLAP） | 单文件 `tupai.duckdb`，进程内嵌入，零服务端 |
| 主键策略 | `UUID` + `gen_random_uuid()` | 全局唯一，避免自增 ID 跨场景冲突 |
| 半结构化 | `JSON` 原生类型（非 TEXT） | 支持 `->`、`->>`、`json_extract` 直接查询 |
| 向量 | `FLOAT[384]` 定长数组 | 对应 all-MiniLM-L6-v2（384 维） |
| 自增 | `SEQUENCE` + `nextval()` | 用于业务序列号（如 `task_no`） |
| 时间 | `TIMESTAMP WITH TIME ZONE` | 本地时区感知，避免 UTC 混淆 |
| 场景隔离 | 单 DB + `scene` 列 + CHECK + 索引前缀 | 方案 A（推荐），物理隔离见 §13.3 |
| 典型数据量 | 80–600 MB | 含日志/资产索引/embedding |

### 13.2 完整 DDL（DuckDB 语法）

> 执行前先加载扩展：`INSTALL fts; INSTALL vss; LOAD fts; LOAD vss;`
> 7 张核心表的完整 DDL 详见 `src-tauri/migrations/001_init_schema.sql`，含 UUID 主键、JSON 列、CHECK 约束、场景前缀索引。

| 表名 | 用途 | 关键字段 |
|---|---|---|
| `schema_meta` | 迁移版本元表 | version PK / name / checksum |
| `worker_task_log` | Worker 执行任务日志 | UUID PK / scene / task_kind / status / params(JSON) / result(JSON) / latency_ms |
| `teach_record_log` | 示教录制步骤日志 | UUID PK / scene / session_id / op_layer(cdp/uia/ocr/vlm) / op_type / target(JSON) |
| `scene_asset_index` | 场景文件资产索引 | UUID PK / scene / file_path / content_text / embedding(FLOAT[384]) |
| `skill_version_manage` | 技能版本管理 | (skill_id, version) PK / scene / source / state / skill_md / gray_success_rate |
| `mcp_connect_log` | MCP 连接日志 | UUID PK / scene / server_name / transport / event / direction |
| `skill_score_eval` | 技能评估打分 | UUID PK / scene / (skill_id, version) FK / 4 维度分数 / total_score / verdict |
| `skill_auto_iter_draft` | AutoSkill 自动迭代草稿 | UUID PK / scene / skill_id / draft_version / iter_reason / optimized_md / status |

### 13.3 场景隔离方案（方案 A：单 DB + scene 列）

#### 13.3.1 方案对比与选型

| 方案 | 实现 | 优点 | 缺点 | 选型 |
|---|---|---|---|---|
| A. 单 DB + scene 列 + CHECK | 所有表加 `scene` 列，CHECK + 索引前缀 | 跨场景统计一次查询；运维简单；备份单文件 | 需强制过滤 | ✅ 推荐 |
| B. 三 DB 物理隔离 | `tupai_work.duckdb` / `_personal` / `_hobby` | 强隔离；单库体积小 | 跨库 JOIN 需 ATTACH；备份复杂 | ✗ |
| C. 单 DB + Schema 隔离 | `work.worker_task_log` 等 | 介于 A/B 之间 | DuckDB schema 支持弱；迁移麻烦 | ✗ |

**选 A**：所有 7 张表均带 `scene` 列 + `CHECK (scene IN ('work','personal','hobby'))`，所有索引以 `scene` 为前导列，保证场景过滤走索引。

#### 13.3.2 查询强制场景过滤（Rust 端 SceneScope）

> 通过 `SceneScope` 类型强制所有 DAO 方法首参注入 scene 过滤，SQL 构造时调用 `scope.filter(sql)`，未注入 scene 的 PR 不允许合入（CI 静态检查 SQL 字符串是否含 `scene`）。

### 13.4 FTS 全文检索索引

> DuckDB FTS 扩展（`INSTALL fts; LOAD fts;`）。中文先经 jieba 预分词写入 `_tokens` 列，再入 FTS，规避 FTS5 默认 unicode61 中文不分词问题。

#### 13.4.1 中文分词预处理流水线

> 原文 `content_text` → jieba 切词（精确模式 + 业务词典）→ 拼接为空格分隔 token 串 → 写入 `*_tokens` 冗余列 → FTS 索引建在 `*_tokens` 上。

#### 13.4.2 三张 FTS 虚拟表

> `skill_fts`（技能名+描述+SKILL.md 内容）、`asset_fts`（文件名+抽取内容）、`teach_fts`（操作描述+目标节点文本），均使用 `fts5` 引擎 + `unicode61` tokenizer。

#### 13.4.3 同步触发（Rust 端显式写入，非触发器）

> DuckDB FTS 不支持自动触发器同步，采用应用层双写：写入主表后同步 `INSERT INTO <fts>`（或 `DELETE` + 重建行）。封装在 DAO 的 `insert_*` / `update_*` 中。

### 13.5 向量检索索引（HNSW）

> DuckDB VSS 扩展（`INSTALL vss; LOAD vss;`），384 维对应 all-MiniLM-L6-v2。HNSW 参数 `m=16, ef_construction=64`，检索时 `SET hnsw_ef_search = 128`。

#### 13.5.1 检索示例

> 文档语义检索：`ORDER BY embedding <-> $query_vector LIMIT 10`；技能语义去重：cosine 距离 < 0.08 判重。
> **FTS + 向量混合**：先各自召回 Top-K，再按 `α·BM25 + (1-α)·cosine` 加权融合排序（α 默认 0.5，可配置）。

### 13.6 文件存储决策表

| 数据类型 | 存储位置 | 是否入 DuckDB | 理由 |
|---|---|---|---|
| `im_config.json`（IM/Worker 配置） | 保留文件（`user_data/config/`） | 否（仅启动读取） | 高频读低频写；人可编辑；配置类不宜入库 |
| session 会话 JSON | 保留文件（`user_data/sessions/`） | 否（仅元信息索引） | 大对象、低结构化；会话体量大 |
| 技能 `.md` 文件 | 保留文件（`skills/<scene>/`） | 是（`skill_version_manage.skill_md` 存快照 + `skill_path` 存路径） | 文件为执行源；DB 存快照用于版本对比/回滚 |
| 示教录制 `recording.jsonl` | 保留原始文件 | 是（结构化步骤入 `teach_record_log`，原始事件存 `raw_event`） | 文件作回放源；DB 步骤支持检索/统计/泛化 |
| 截图 PNG | 保留文件（`user_data/screenshots/`） | 否（仅存 `screenshot` 相对路径） | 二进制大对象不入库；路径引用即可 |
| 文档原文（PDF/Word/...） | 保留文件 | 是（抽取文本入 `scene_asset_index.content_text`） | 原文供预览；抽取文本供 FTS + 向量 |
| 向量 embedding | 入 DuckDB（`FLOAT[384]` 列） | 是 | 检索时实时计算距离，需结构化存储 |
| `tupai.db`（SQLite 旧库） | 迁移完成后废弃 | 迁移源 | 见 §13.8 迁移计划 |
| 新结构化业务数据 | DuckDB `tupai.duckdb` | 是 | 唯一本地结构化存储 |

### 13.7 Rust 集成方案

#### 13.7.1 依赖与连接池

> `duckdb = { version = "1.1", features = ["bundled", "vss", "fts"] }` + `r2d2` 连接池（max_size=4），`DuckdbConnectionManager` 实现 `r2d2::ManageConnection`，启动即迁移。

#### 13.7.2 版本化迁移机制

> 版本化 SQL 文件位于 `src-tauri/migrations/`（001_init_schema / 002_fts_indexes / 003_vector_indexes / 004_sqlite_migration），`migrator.rs` 读取 `schema_meta` 表按序应用未执行版本，记录 checksum 防篡改。

#### 13.7.3 备份策略

| 策略 | 命令 | 频率 | 用途 |
|---|---|---|---|
| CHECKPOINT | `CHECKPOINT;`（应用层定期调用） | 每 5 分钟 / 退出时 | 刷 WAL 到主文件，防崩溃丢数据 |
| COPY DATABASE | `COPY (FROM tupai.duckdb) TO 'backup_tupai.duckdb';` 或文件级复制 | 每日 / 版本升级前 | 全量冷备 |
| 版本快照 | 技能替换前 `snapshot_path` 备份旧 `.md` | 技能迭代时 | 单技能回滚 |

> **数据量估算**：典型 80–600 MB（日志 ~50–400 MB + 资产索引文本 ~20–150 MB + embedding ~10–50 MB）。DuckDB 列存压缩比约 3–5x，实际磁盘占用约为原始数据的 25–35%。

### 13.8 与现有 SQLite 的迁移计划

> 三阶段平滑迁移，保证零数据丢失、可回退。与 Rust 轨道 B-4~B-6 阶段并行。

#### Phase 1：DuckDB 并存（新数据双写 DuckDB）

| 项 | 说明 |
|---|---|
| 时长 | 1–2 周 |
| 动作 | 新建 `tupai.duckdb`，应用 §13.2 全部 DDL + §13.4 FTS + §13.5 HNSW；新业务写入 DuckDB |
| SQLite 状态 | 保留只读，旧查询路径暂不切换 |
| 读策略 | 新数据从 DuckDB 读；历史数据仍从 SQLite 读 |
| 风险 | 双写期需保证一致性（DuckDB 写成功后再提交 SQLite 侧状态，或 DuckDB 为唯一新写入端） |
| 回退 | 若 DuckDB 异常，停用新写入，回退 SQLite（新数据已落 DuckDB 需手动导出） |

#### Phase 2：SQLite 历史数据迁移脚本

| 项 | 说明 |
|---|---|
| 时长 | 1 周（含验证） |
| 动作 | 执行 `004_sqlite_migration.sql`：ATTACH 旧 `tupai.db` → 逐表 `INSERT INTO duckdb_table SELECT ... FROM sqlite_table`（字段映射 + scene 默认填充 `work`） |
| 映射关键 | `skill_versions` → `skill_version_manage`；`skill_runs` → `worker_task_log`（task_kind='skill_call'）；`skill_evaluations` → `skill_score_eval`；`skill_fts` 重建 |
| 验证 | 行数对比 + 抽样字段比对 + FTS/向量索引重建后检索测试 |
| 双跑期 | 迁移后保留 SQLite 只读 2 周，对比查询结果一致性 |

#### Phase 3：废弃 SQLite

| 项 | 说明 |
|---|---|
| 时长 | 1 周 |
| 动作 | 移除 `rusqlite` 依赖；删除 `tupai.db`（保留 `.bak` 冷备 30 天）；移除 SQLite 相关 DAO/连接代码；`schema/app.sql` 标记废弃 |
| 验收 | `cargo tree` 无 `rusqlite`；全功能回归通过；DuckDB 单一存储 |
| 不可逆 | 此阶段后 SQLite 不可恢复（仅 `.bak` 保留） |

### 13.9 索引与查询性能要点

| 查询模式 | 走索引 | 备注 |
|---|---|---|
| 场景内任务列表 | `idx_wtl_scene_started` | 覆盖索引，避免回表 |
| 技能历史评估 | `idx_sse_scene_skill` | (scene, skill_id, version) 精确前缀 |
| 待确认草稿 | `idx_sid_pending` | 部分索引，仅扫未决草稿 |
| 文档语义检索 | `idx_asset_embedding` (HNSW) | ef_search 可调（默认 64） |
| 技能语义去重 | `idx_skill_embedding` (HNSW) | 阈值 0.08（cosine 距离） |
| 全文检索 | `*_fts` (fts5) | 中文经 jieba 预分词 |

> **HNSW 参数**：`m=16, ef_construction=64` 适合 80–600 MB 数据量；检索时 `SET hnsw_ef_search = 128;` 提升召回率。
