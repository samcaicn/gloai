# Mika 远端 Issue 深度分析

**日期**：2026-11-18
**范围**：95 个 open issue（全量拉取后逐条读正文与评论）。**PR 由另一个分支单独处理，本文聚焦 issue 本体**（只在下文标注「已有 PR 在途」以决定是等 PR 还是自己修，不做 PR 评审）。
**主线**：哪些 bug 该修、哪些功能值得加、以及按什么顺序动。
**项目规则更新（2026-11-18）**：改为「功能最大化、能力最大化」——外部项目（magpie、AppFunctions、Google 连接器、第三方 Skill 等）可以接入/引用，不再一刀切禁止外部痕迹。评估 issue 按能力价值，不再因「点名外部项目」而拒。

## 0. 总体结论（先说人话）

1. **最大的一个系统性 bug 是「返回键（back）注入失效」**。10 台以上的小米/红米设备（Android 15/16/17）自检第 7 项都是 `back failed`，而 tap/type/scroll 全过。这不是单机个案，是**同一根因的一族**，应当按「根因类」一次修掉，而不是逐条 issue 追。目前你在测试机上复现不了，但它已经是最高频的一类兼容性报告。
2. **第二大一类是「自绘界面（微信/小程序/GitHub 客户端）无障碍节点为空」**，表现为点不动、读不到、OCR 也读不到，最后进 `no_progress` 熔断。根因在目标 App 的渲染方式（自绘/Flutter/反自动化），**Mika 能做的是「检测到该 App 不响应注入 + 无障碍为空 → 明确报错并降级」**，而不是无限重试或把「没反应」当成功。
3. **音频焦点/静音是一族真 bug**：#483/#228/#588 同属「虚拟屏抢占或静音逻辑泄漏到前台」，机制已定位（`PLAY_AUDIO ignore` 不阻止 requestAudioFocus）。
4. **远程解锁/定时唤醒是另一族**：荣耀 MagicOS、vivo OriginOS、ColorOS 各自在锁屏页识别上有偏差。你已经在按「能力检测 + 降级」的思路推进（#453 已本地修、#307 已定位到 `display_windows=0`），方向对，继续收口即可。
5. **功能侧最有价值、且已有 PR 在途的**：备份恢复（#166/#185）、Shizuku 第二条路（#204/#230）、人格+模型组+思考档位（#292/#288/#306）、语音播报（#207/#445/#455）、Mika Anywhere Web 控制台（#372/#381）、远端执行环境（#366/#277）。这些**优先做 PR 评审**，而不是新开功能。
6. **几个低成本快赢**值得顺手收：Keenable 搜索（#516）、QQ 音乐/人人视频知识（#164）、土耳其语（#646）、lightSteps 默认开 + 定时半价时段（#239）、web_search 选路提示词（#672）、CLI 版本不匹配提示（#314）。

## 1. Bug 分析

### 1.1 系统性 bug（同根因，最高优先级）

#### 1.1.1 「back 失败」族 —— 当前最该修

**涉及 issue**：#622、#642、#469、#450、#299、#225、#221、#220、#209（以及 #80 的 A12 变体）

**共同现象**：自检第 7 项 `actions` 里 `tap ok / type ASCII ok / type Chinese ok / scroll ok / back failed`，其余 11 项全过。任务侧表现为 `no_progress` 熔断（#622 给了两次真实 run_id 的完整记录）。

**关键证据（#622 的推断，方向大概率对）**：back 与 tap/type/scroll 走的是**不同的注入通道**。tap/type/scroll 是坐标/文本注入，back 是**全局键事件（KEYCODE_BACK）**；在 `displayId != 0` 的虚拟屏上，键事件可能被系统丢弃或不路由到前台 task。所以「点了没反应 → 画面无变化 → no_progress」。

**为什么你复现不了**：这批报告几乎全是小米/红米 + HyperOS（Android 15/16/17），你手头的测试机不在这个组合里。`#211`（建屏后设成全屏）可能缓解了一部分，但 0.1.42/0.1.43 仍有报告，说明没根治。

**建议的修法（按根因类，不是逐机特判）**：
1. 先确认 back 的实现路径（`phone_back` / 自检第 7 项），看它到底发的是 `KEYCODE_BACK` 还是无障碍 `performGlobalAction(GLOBAL_ACTION_BACK)`，二者在虚拟屏上的路由语义不同。
2. 把「back 无效果」的判定做成通用的「注入后画面无变化」检测（复用 #461 已做的补点检测思路）。
3. **降级链**：back 无效果时，回退到「点当前页左上角可见返回控件」→ 再回退到「点导航栏/手势返回区域」→ 仍无效果才计入 no_progress。
4. 这条降级一旦落地，会同时救下 #622 的任务侧熔断、以及所有 back 失败的自检项。

> 按项目「fix by root-cause class」原则，这一族**合并在一个修复里**做，不要在每台机器上追。

#### 1.1.2 「自绘界面无障碍为空 + 注入无效」族

**涉及 issue**：#237（微信主界面）、#92（微信发消息）、#421（GitHub 客户端点击无效）、#471（微信小程序 OCR 读不到）、#201（微信输入）、#225（GitHub 页面点不动读不到）

**共同根因**：目标 App 的页面是自绘/Flutter 或做了反自动化处理，对外不暴露无障碍节点（`treeQuality: unusable`、`elements: []`），同时注入的指针事件不被消费。Mika 目前「看得见文字，但点不动也读不到控件」。

**这里要拆成两个不同问题，别混为一谈**：
- **A. 注入点击被丢弃**（#237/#421/#92/#201/#225）：需要区分「没送到」和「送到了被丢弃」。#237 的提议很好：连续 2–3 次点击 `no_effect` + 无障碍树为空 ⇒ 判定「该 App 不响应注入点击」，明确告知用户，停止无限重试。
- **B. 本地 OCR 读不到但有图**（#471）：截图有内容、看图模型能完整读出、但本地 OCR 返回空。这是 OCR 引擎对某类字体/表单的识别问题，跟 A 不是一回事，要单独查（需要 reporter 补截图 + 诊断）。

**建议**：
1. 落地「注入无效」的明确失败类型 + 降级通道（#237 第 1、2 点），这是通用机制，不针对微信。
2. #471 的 OCR 空值单独走「要截图定位」的路径（你已经回了要证据）。
3. 微信这类 App 能点动的场景（列表页能点、会话页不能）说明不是「微信整体不可用」，是「会话页自绘」。这类**知识层**上可以沉淀一条「微信会话页无障碍为空，需走截图定位」的 APP 知识。

#### 1.1.3 音频焦点/静音族

**涉及 issue**：#483（后台虚拟屏跑任务时前台抖音/B 站没声音）、#228（执行后台任务导致全局静音）、#588（小窗声音开关只能开不能关）

**根因（你已定位）**：任务期间对虚拟屏 App 做 `appops PLAY_AUDIO ignore` 只让它「没声音」，但**不阻止它 requestAudioFocus**；虚拟屏里的 App 一出声就抢走前台播放器的音频焦点。任务结束释放后恢复。

**建议**：
1. #483/#228 是同一机制的两种表现：让虚拟屏 App 不抢焦点（或把虚拟屏音频路由到哑设备）。`dumpsys audio` 的 focus stack 能确认是哪个 uid 抢焦点，你已经回了这个诊断请求，等数据。
2. #588 是另一层：小窗声音开关的 toggle 状态管理，你已经加了诊断日志（`togglePipSound` / `could not mute again`），**需要真机复现日志才能定位**，先挂着等数据，不要靠读代码硬猜。

#### 1.1.4 远程解锁/定时唤醒族

**涉及 issue**：#307（荣耀 MagicOS）、#453（vivo iQOO）、#430（小米 HyperOS 定时）、#358（小米锁屏定时）、#570（一加 ColorOS 指纹）、#623（vivo AI 电话权限）

**状态**：
- #453 已在本地修（回退点击「用密码」+ 按残留输入清空，不再盲发 16 次 DEL），未发布。
- #307 已定位到 `display_windows=0`：MagicOS 锁屏时无障碍窗口列表整个为空，`getWindows()` 返回空。这是**厂商把锁屏窗口对无障碍不可见**，不是包名/类型匹配问题。方向上只能做「能力检测 + 明确报错」，钻荣耀私有实现既违反项目规则也未必稳。
- #570 指纹优先页拦在 PIN 前面（ColorOS），和 #453 同类。
- #358/#430 是定时任务到点「未触发/未亮屏/未解锁」——#430 有诊断显示 `write secure settings: not granted`，可能是「闹钟没把进程拉起」这层，跟解锁是两码事，要分开看。

**建议**：
1. #453/#570 的「生物识别优先页 + 空框 DEL」修复随下版发布后统一真机验证，这一族能收掉大半。
2. #307 明确为「该 ROM 锁屏无障碍不可见」的已知限制，给出清晰提示，不再投入钻私有实现。
3. #358/#430 单独查「精确闹钟到点是否触发」这一层（`setExactAndAllowWhileIdle` + Doze + 厂商杀后台），别和「解锁」混在一个 issue 里。

#### 1.1.5 配对/连接族

**涉及 issue**：#440（helper handoff timeout）、#278（自动开无障碍/无线调试失败）、#302（Connected but couldn't get ready）、#274（ChatGPT 登录卡住）

## 4. 附：几个贯穿性提醒

1. **设备侧瓶颈 ≠ 代码 bug**：#695、#307、#570 这类「厂商 ROM 行为」，app 能做的正确姿势是「能力检测 + 明确报错 + 优雅降级」，不是去钻厂商私有实现（项目规则）。

4. **判断 UI bug 用 perf 包**（debug 包慢 7–10x），判断「卡」类问题别用 debug 包下结论。
